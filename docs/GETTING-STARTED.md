## Requirements

Windows needs Node.js 24.21.0 or newer and npm. macOS needs native Node.js 24+ and Git. Install and sign in to at least one executor: Claude Code, Codex CLI, Grok CLI or Cursor CLI, or add an API key. Claude Code on Windows also needs Git for Windows.

## Connect a server

Add the server and its SSH host alias to `remote-servers.json`. Choose the unconnected server in the `@@@` menu or select **Connect** under **Usage & connections > Remote servers**, then confirm. If setup needs a command, copy it, run it on the server and select **Check again**. Alternatively, with PugPort running, run `pugport node add --tunnel <alias>` in the terminal. Sign in once to a CLI on that server, for example with `claude login` or `codex login`, then mention it in chat as `@@@<name>`.

To disconnect, select **Disconnect** on the remote server card and confirm. The app removes the local pairing, closes the SSH tunnel and uninstalls the node service. Select **Also delete PugPort from the server** to remove its program and data too. If SSH uninstall fails after the local pairing is removed, use **Retry uninstall** on the card; it keeps the same deletion choice.

The server node listens only on `127.0.0.1`; it trusts every user on that machine. The desktop opens an SSH tunnel when a task needs it. Use this only on a machine whose local users you trust.

After a server is connected, the computer that connected it (or any computer whose own SSH alias reaches it) sets up **account access** automatically: a PugPort key that can only forward to the node's port. The key syncs with your account, so another computer signed in to the same account can use the server, see its live status and send it tasks without any SSH setup of its own. Disconnecting, and installing or updating the node, still need a computer with full SSH access. If a computer has neither its own SSH alias nor account access yet, the card says so; open PugPort once on a computer that can reach the server over SSH.

## Set up on Windows

```powershell
git clone https://github.com/pugport/pugport.git
cd pugport
.\Setup-Windows.ps1        # local Node runtime, dependencies, tests, build
.\Start-PugPort.cmd    # desktop app
```

If PowerShell blocks the script, run `powershell -ExecutionPolicy Bypass -File .\Setup-Windows.ps1`; this applies to that one run only.

Or run `launchers/Start-Web.cmd` and open <http://127.0.0.1:4317>.

The desktop normally uses loopback port 4317. If Windows reserves it or another program occupies it, the desktop selects an available loopback port before startup. An explicit `COMBORUNNER_PORT` or `AGENT_STUDIO_PORT` keeps its value and reports a bind failure instead. The web-only launcher keeps its configured port.

The terminal command, MCP server and local device node discover the running desktop's selected port through a per-user `desktop-endpoint.json` file (Windows: `%USERPROFILE%\.pugport`, also written to `%LOCALAPPDATA%\ComboRunner` for older clients, because a desktop started by a packaged app such as Codex has its AppData writes redirected into that app's private folder; macOS: `~/Library/Application Support/PugPort`; Linux: `$XDG_DATA_HOME/pugport` or `~/.local/share/pugport`). It contains a port and desktop process identity, with no session tokens or executable settings. The desktop publishes it only after its owned backend is ready and removes its own entry on exit; dead-process entries are ignored. Explicit client `PUGPORT_PORT`, `COMBORUNNER_PORT` or `AGENT_STUDIO_PORT` settings take priority. New MCP connections generated by the desktop use discovery; older saved entries with an explicit port remain pinned until reconnected through Extensions → Connections.

## Set up on macOS

Use native Node.js 24+ and Git. On Apple Silicon, use arm64 Node and install dependencies on the Mac; do not copy Windows `node_modules` or `.runtime`.

```sh
git clone https://github.com/pugport/pugport.git
cd pugport
bash launchers/setup-macos.sh
bash launchers/start-macos.command
```

Setup installs locked dependencies and runs type checks, tests and a build. To rebuild later, quit PugPort from its menu, run `npm run build`, then start it again. For a local unsigned application bundle, run `npm run package:desktop` after a successful build. On Apple Silicon the result is `release/PugPort-darwin-arm64/PugPort.app`; Intel uses `darwin-x64` and requires a native Intel build. See [Mac setup and validation limits](MAC-PORT.md) before using it as your daily desktop. This does not produce a signed/notarized release or configure updates.

## Connect executors and bots

PugPort scans for official CLIs on startup and refresh. **Usage & connections** shows installed clients and their reported account/connection state. Missing default clients stay out of the main list; use **Install or connect a client** for installation options, then **Refresh** to detect a new installation. Configured API accounts, managed accounts and custom executors remain visible when they need attention.

Add **Muse** or **Grok Bot** through **Usage & connections → Connections → Add → Bot**. After adding one, use its Bot row to sign in, configure usage or set up a Grok routine. Existing configurations are retained; bots you haven't added stay out of the account and usage lists. Use `@` to mention a role or executor, `@@` to mention an enabled bot or device, or `@@@` to mention a remote server.

To add your own endpoint, open **Usage & connections → Connections → Add → API → Custom API**. Select Azure Responses, OpenAI Responses, OpenAI Chat Completions or Anthropic Messages, then enter the endpoint, key and model or deployment name. Local budgets need input and output prices. Missing prices remain unknown. On macOS the form also has **Context and output limits (optional)**: a custom connection otherwise reports a 32,768-token context window and a 4,096-token output limit, which is too small for a local model that reasons before it answers. See [Routing](guides/routing.md) and [expiring API credit](guides/routing.md#expiring-api-credit-and-its-window).

An optional local Bifrost gateway uses this same form; see the [tested connection recipe and limits](BIFROST.md). It is not required for API or native CLI use.

For a separate DeepSeek search key, open **Extensions → Connections → Web search**. Use `/search keywords` (or the Chinese command name `/搜索`) for a direct search, or let an agent call the shared search tools when needed. See [DeepSeek search and its separate spending estimate](DEEPSEEK-SEARCH.md).

## Install optional components

Setup installs the application dependencies and builds the app; it does not download optional local models. In **Extensions → Components**, choose a component, inspect its requirements, then install it. Google/Microsoft Workspace connectors are dormant; existing account data stays on disk.

| Optional capability                   | Approximate installed model size                      | Without it                                                              |
| ------------------------------------- | ----------------------------------------------------- | ----------------------------------------------------------------------- |
| Local speech recognition              | 240 MB                                                | Use text input; cloud transcription is not connected yet                |
| Image semantic search and OCR         | 210 MB                                                | Exact and near-duplicate matching remains available                     |
| Semantic history search               | 590 MB                                                | Keyword history search remains available                                |
| Document conversion      | Depends on the component and its runtime              | Existing project search / file attachment capabilities remain available |

These are model footprints, not the application's total size. Electron and Windows inference libraries remain in the base package. Installed components live outside the installed application so upgrades need not download them again; old local component locations remain readable. `Setup-Windows.ps1 -WithLocalComponents` opts into installing the optional components during developer setup.

## Download a Windows review build

A repository maintainer can open **Actions → PugPort checks → Run workflow**. After checks pass, the run publishes a **14-day Actions artifact** with a Windows portable ZIP, `SHA256SUMS.txt` and a file inventory. Extract the whole folder and run `PugPort.exe`; do not copy only the executable. The filename records the version and commit, so testers can report exactly which build they used. Access follows repository permissions. This is an unsigned review build, not an automatic GitHub Release or an in-app updater.

## Everyday use

In **Settings → Smart routing**, name and save reusable routing rules, then choose a profile from the executor menu below a chat. **Automatic** keeps the existing global and chat settings. Profiles use local rule parsing and do not add a model request to each message. Fixed platform/order preferences are off by default and live under **Advanced**; only connected CLI/API candidates are offered. See [routing profiles and rules](guides/routing.md#routing-profiles-and-rules).

New chat reuses the empty chat just created in this window when it is still selected and the project, privacy and collaboration mode match. If it contains a draft, quote, attachment, message, task or Mod workspace, New chat creates a separate chat. Existing empty chats are not deleted or merged.

Select an executor or provider to use it directly; usage limit, model capability and file permission checks still apply. Automatic routing uses local rules. Enter sends, Shift+Enter inserts a newline, and confirming an IME candidate never sends. Ctrl/Cmd+Enter remains available.

Project file scope guides task instructions and result checks. It does not provide operating-system isolation; the selected native CLI and its sandbox determine actual file access.

To continue with another provider, choose it in the same chat and send your next message. Recent messages, project memory and archive paths carry over; interrupted tasks also supply bounded saved output. Native sessions are not shared across providers. The old workflow's Continue button retains that workflow's original settings.

Closing the window hides the app to the tray, so queued work keeps running. Choose **Quit PugPort** from the tray menu to exit.

## Find your data

Removed projects are managed under **Settings → Chats**, rather than at the bottom of the sidebar. Expand a project to inspect its app-owned data, restore it, or confirm permanent cleanup. Original linked project folders remain; explicitly app-created chat workspaces are listed separately for deletion. Related scheduled tasks are disclosed and paused. Cleanup reports actual file bytes freed; deleting records makes shared SQLite pages reusable and does not claim that the database file shrank. Partially completed cleanup must be retried before restoration.

Data stays local: `.data/` for source runs, `%APPDATA%/ComboRunner/data/` for packaged builds, or wherever `COMBORUNNER_DATA_DIR` points. Full chat exports use `%LOCALAPPDATA%/ComboRunner/memory/` by default. CLI memory is opt-in per project and writes only read-only pointers into that project. Both exports and SQLite contain plaintext; cloud-synced data directories may sync them. You can disable file exports in project settings.

For source runs, `.data/data-location.json` is the recommended way to keep data outside OneDrive or another synced folder. Choose **Quit PugPort** from the tray first, back up and copy the complete data folder to a location outside the synced folder, then write `{ "dataDir": "C:\\PugPortData" }` to the location file in the checkout (use your actual absolute path). The target must already contain `studio.sqlite`; startup never creates a missing target or falls back when the file exists. `COMBORUNNER_DATA_DIR`, then the legacy `AGENT_STUDIO_DATA_DIR`, still take precedence. Remove stale overrides pointing to the old `.data`: a folder containing `data-location.json` is a moved-folder stub and cannot be opened as data. Packaged builds ignore the location file. Git worktrees have no location file, so development runs there keep their own `.data` unless an environment override is set.

Source diagnostics report the effective data directory and location file, and do not migrate data. Source and packaged defaults are separate; a different history after changing entry points does not by itself mean data was lost. Scripts can request a graceful exit with `electron . --quit`: it refuses without a dialog when work or an incognito chat is open, or task state is unknown. Future scheduled tasks alone do not block it. The caller must poll for exit and report its own timeout.

See [the feature removal decision](decisions/2026-10-14-portable-feature-trim.md) for legacy runtime cleanup, the optional Everything service uninstall command, and compatibility changes.
