# Features

The full feature list behind the [README](../README.md) highlights and the [User guides](guides/README.md).

- **One chat, many agents.** Ask a question or describe a task; attach a project folder only when you need file access. Questions run read-only; changes need an explicit request.
- **Mention participants.** Type `@` to mention roles or executors, or `@@` to mention devices and bots. In project chats, `@` also offers project files. `@@@` also mentions servers connected over SSH.
- **Usage-aware routing.** Picks the executor, model and reasoning effort based on the task, what each CLI actually reports, and which limit windows reset soonest. Switch to “Suggest, then confirm” if you want the final say.
- **Straight-line pacing, reset cards and expiring API credit.** Compares subscription windows against a straight-line spend curve and predicted waste before reset, factors Codex reset cards into pacing (with optional auto-redemption), paces expiring API credit over a 14-day window, and keeps warm 5-minute prompt caches on the same account until it falls ahead of pace.
- **Routing profiles and Cursor fallback.** Save up to 30 named routing profiles with local natural-language rule parsing, model exclusions (`*` wildcards), and same-model fallback through Cursor when a service's native accounts are below their reserve or cooling down.
- **Executor failure notices and cooldown.** Cursor and Claude check execution flags during discovery. Inbox shows incompatible CLI startup errors, network-wide outages and repeated executor failures; repeated technical failures put an account in a 1, 5, 15 or 60-minute cooldown that automatic routing skips while manual pins still run.
- **Executor diagnosis.** An eligible tool-free executor can explain a failure in its Inbox notice using bounded, redacted evidence; suggested changes are marked unverified.
- **Nightly CLI updates.** Cursor and Grok update serially during a quiet overnight window; repeated failures or a broken CLI appear in Inbox.
- **Reliable executor outcomes.** Host-measured Git changes help confirm file results per path; Claude empty sessions and Grok permission denials retain their failure source.
- **Planned execution.** A selected native CLI plans and executes internally; automatic multi-provider workflows can use a read-only plan of up to 6 steps. Optional verification commands check the result.
- **Automatic handoff.** Automatic tasks can hand unfinished work to an available executor after reaching a usage limit, carrying verified native tool checkpoints and accepted follow-ups. Unconfirmed writes are checked before continuing; explicit account pins remain binding.
- **Honest usage ledger.** Official usage limit readings with source and timestamp. Token and cost usage is recorded per project, executor, model and run. Unknown values stay unknown instead of being guessed. Cursor's model pools and credits can refresh after the CLI and editor account identities are verified; manual snapshots remain available when a service doesn't report a value.
- **Remote servers.** List rented cloud machines in `remote-servers.json` in the data folder and they appear under **Usage & connections**, after Devices, with the days left before each trial or credit ends. Expiries within 14 days are highlighted and past ones are marked. Only `name` is required; `expiresOn` is a `YYYY-MM-DD` day and `credit` is free text you update yourself. Add `ssh` (a Host alias from your own SSH config) to see CPU, memory and disk like a device card, `services` (systemd names or patterns such as `actions.runner.*`) to see whether they run, and `statusCommand` for one short read-only status line. Example: `{ "servers": [{ "name": "test-box", "provider": "Example Cloud", "region": "us-east", "spec": "4 vCPU · 16 GB", "purpose": "CI runner", "expiresOn": "2026-11-30", "ssh": "test-box", "services": ["actions.runner.*"] }] }`. The file holds no addresses or keys. PugPort uses key login only, checks each box at most every 3 minutes and only while the page is open, and its status checks install and write nothing on it. Jobs you define can push to a bare repository and write their own log directory, `~/.pugport-jobs`. To connect a server with an SSH alias, select it in the `@@@` menu or choose **Connect** on its remote server card and confirm. The app installs and pairs a loopback-only node; sign in to a CLI on the server once. Choose **Disconnect** on the card to revoke the pairing, close the tunnel and uninstall the node service. Select the checkbox to also delete the server's PugPort program and data. If SSH uninstall fails after local removal, the card offers **Retry uninstall** with the same deletion choice. A connected server also gets **account access**: a PugPort key that can only forward to the node's port, set up automatically from a computer with its own SSH alias and synced with your account. Other computers signed in to the account then reach the server, its live status (from the node, without a shell) and its tasks without their own SSH setup; `statusCommand`, disconnecting and node installs still need full SSH.
- **Permission ceiling.** Dispatched executors inherit the dispatcher's network access and, in a linked worktree or work lane, local Git commits, never more. A status line on each run shows what was inherited and which executors PugPort cannot enforce. See [Project development workflows](project-development-workflows.md#permission-ceiling).
- **Owner card for push, pull request and merge.** A writable networked run can push the current branch, open a pull request or merge one only through three host tools. Each waits for an owner card. PugPort does not force-push. A merged or closed pull request stops its monitor. A blocked run keeps the executor's own summary.
- **Work lane result delivery.** Results reach a running coordinator with other-agent provenance and durable collaboration mail. Long results are saved as files readable with `read_document`; external task results expose the file path, and conversation work lists include lane state and the last saved result.
- **Coordinator plans and feedback.** Ordinary conversations can show a plan linked to work lines. Foreground main tasks can ask through a Question card and save project rules backed by the user's exact words, with notices to other active project runs and removal in project settings. Brief review guidance precedes implementation; Review notes distinguish must fix, should fix and nit findings. See [Project development workflows](project-development-workflows.md#plans-questions-and-project-rules).
- **Work modes.** The mode chip next to **+** switches a chat to **Mods author** (build, load and debug a Mod in the chat's own folder, with a Debug menu and a Local build in the Store) or **Navigator** (a read-only lead plans, delegates, reviews and sums up on the executor you choose, re-routed with a note when it's unavailable). Mode instructions never enter memory. See [Work modes](WORK-MODES.md).
- **Persistent queue.** Different chats run concurrently; messages within one chat stay ordered and writes to the same project are serialized. Deadlines and priorities survive restarts.
- **Mid-task follow-ups.** Supported Codex, Grok, Pi and modern Claude transports accept follow-ups in the current chat. Receipt failures are kept visible and never silently replayed. Changing tools or permissions starts a new session with local context.
- **Message queue and side chats.** Steer, edit, cancel or reorder queued messages. Independent side chats inherit the model selection and read fresh main-chat context for each question. Reopen them from side-chat history; their records stay separate from the main sidebar and main-chat memory.
- **Clear completion status.** A finished reply is separate from verified execution. Executor reports of partial or blocked work remain unfinished; missing evidence stays unverified. Thought streams follow the bottom until you scroll up.
- **Executors calling executors.** Name an account card in your task (“ask a named account to review”) and a running Codex, Claude or Grok hands the subtask to that executor through a local MCP endpoint and gets the result back. The parent releases its execution slot while waiting, then reacquires a slot to continue. Works across local and isolated sign-ins; cards can be renamed. Subtasks are read-only by default and can't call further.
- **Independent subtask routing.** Automatic children choose their own model and effort from their task, usage left and current load. Numbered progress stays in the stage where it arrives, including after follow-ups.
- **Resumable local media analysis.** Adaptive local fingerprints retrieve bounded image/video candidates; a fixed local program then checks geometry and time alignment. Checkpoints avoid repeated work. No embedding model is required. Visual matches remain evidence for review, never automatic deletion permission.
- **Portable local workflows.** Copy and edit media-analysis parameters, export JSON, or preview and import a third-party HTTPS recipe. Directories are selected per run. Open **More → Local workflows** in a chat or manage recipes under **Extensions → Components → Local workflows**.
- **Resume where it stopped.** Continue a stopped or interrupted task on the same executor, model and native session; multi-step plans skip finished steps without re-planning.
- **Attachments.** Drag files in or paste images; images are passed to Codex and Claude as vision input.
- **Local history retrieval.** MiniSearch ranks relevant historical excerpts with source metadata and checked file paths before a task starts. Indexing and archive sync run in background workers, without paid embedding calls.
- **Read-only Git.** Tasks can inspect local history, diffs, status and refs through the shared Git tool, including read-only Claude tasks. PugPort checks a strict allowlist and disables external diff/textconv programs and lazy fetching. Read-only Grok tasks get these tools too; if one calls the user's other MCP servers, PugPort refuses and the task stops.
- **GitHub.** Off by default in Settings. One connection uses this computer's gh sign-in to share GitHub issues, pull requests, commits, files and Actions logs with executors. Write tasks can create branches, commit files, open pull requests and comment in any repository your gh account can write. Merging, deleting files, creating or forking repositories, running Actions, closing or reopening issues or pull requests, marking duplicate issues, approving reviews, and writing to the default branch ask you first. A failed default-branch lookup also asks. Tasks started in the first seconds after launch, before the background connection is ready, do not see them. GitHub adds 25 read tools and 18 write tools; Cursor and Pi fail tasks whose bridge list exceeds 256 tools.
- **Optional components.** Add skills, MCP tools and local speech/image/history models when needed. The default desktop package doesn't include optional model downloads.
- **Skills per chat.** Installed, enabled Skills remain available on demand. In **Chat settings → Skills**, all boxes start unchecked. Check a Skill to require a relevance check before every later turn in that chat and use it when suitable; changes save immediately. Unchecking removes that preference without disabling the Skill. Tool restrictions still apply.
- **Terminal CLI (`pugport`).** Use `pugport` for a full-screen terminal chat or one-shot commands (`ask`, `status`, `agents`, `tasks`, `cancel`, `doctor`, `open`, `node`) with `stdin`, `--resume` and `--json` output; installed desktop copies add `pugport` to `PATH` automatically.
- **Tailscale device nodes and file transfer.** Pair Linux and macOS headless nodes (`pugport node`) over Tailscale or SSH tunnel, call them with `@@` and `@@@`, and send or receive files up to 16 files / 2 GiB each / 4 GiB total.
- **Pinned messages and conversation branches.** Pin messages to the top of a chat with live task status or manual follow-up tracking, and fork or edit from any message into a new branch.
- **System tray, Quick Chat, keep-awake and Blackout.** Check usage in the tray, open Quick Chat with `Ctrl+Alt+Space`, use the manual or task-based keep-awake controls, and use **Black out now** or `Ctrl+Alt+B` to cover every display until a key is pressed.
- **Sandbox settings.** The bundled MXC SDK 1.0.0 cannot run Learning mode. A turn with web search results uses the CLI sandbox instead of a trusted project’s full access.

## Routing and executors

PugPort routes native CLI and API tasks itself. Pi runs the API task loop; native CLIs use their own adapters. The former bundled Magpie gateway has been removed. Its historical records remain, but new tasks must use an available executor.
